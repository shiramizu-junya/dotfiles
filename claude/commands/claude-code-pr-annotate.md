レビュアーにレビュー依頼する前に、PR の変更内容を確認し、補足コメントが必要な箇所を特定してください。

## 対象PRの特定

$ARGUMENTS が指定されている場合はそのPR番号を使用する。
指定がない場合は、現在のブランチに紐づくPRを取得する。
PRが存在しない場合は「先にPRを作成してください」と案内して終了する。

## 手順

### Step 1: 変更内容の把握
1. PR のタイトル・説明・ベースブランチ・最新コミットSHAを取得する
2. 変更ファイル一覧と差分の詳細を取得する
3. 変更ファイルの全体を読み取り、差分の文脈を理解する
4. PR に既存のコメントがあれば取得し、重複投稿を避けるための情報として保持する

### Step 2: コメントが必要な箇所を特定

以下に該当する箇所を洗い出す：

- **意図が伝わりにくい変更**: なぜその実装方針にしたか、背景がないと誤解されそうな箇所
- **トリッキーなロジック**: 一見すると冗長・不自然に見えるが理由がある実装
- **仕様に基づく判断**: 「なぜこの値？」「なぜこの条件分岐？」とレビュアーが疑問に思いそうな箇所
- **既存コードへの影響**: 他の箇所に影響がないことを補足すべき変更
- **TODO・暫定対応**: 意図的に後回しにしている部分とその理由
- **レビューで見てほしいポイント**: 設計判断に迷った箇所、フィードバックが欲しい箇所

注意: 削除のみの変更（削除行にインラインコメントを付けられない場合）は、最も関連性の高い周辺の残存行にコメントするか、PR全体へのコメントとして扱う。

### Step 3: 結果の提示

洗い出した箇所を以下のフォーマットで一覧提示する：

| # | ファイル:行番号 | コメント種別 | コメント内容（案） |
|---|----------------|------------|------------------|

コメント種別:
- **背景説明**: 実装の意図・経緯を説明
- **注意喚起**: レビュアーに特に見てほしいポイント
- **質問**: レビュアーに判断を仰ぎたい箇所

コメントが不要と判断した場合は「コメント追加不要」と理由を添えて報告する。

**ここで必ずユーザーの確認を取ること。** コメント内容の修正・追加・削除の指示があれば反映する。

### Step 4: 承認後にコメントを追加

ユーザーが承認したコメントのみ、PR のインラインコメントとして投稿する。

投稿には `gh api` を使用し、以下の情報を含める：
- `path`: 対象ファイルパス
- `line`: 対象行番号（diff ではなく変更後ファイルの行番号）
- `body`: コメント本文
- `commit_id`: PR の最新コミット SHA
- `subject_type`: `"line"`

既存のコメントと同じファイル・同じ行番号に同趣旨のコメントがある場合はスキップする。

全コメントの投稿が完了したら、追加したコメント数とスキップしたコメント数を報告する。
