以下のコードレビューチェックリストに基づいて、変更内容をレビューしてください。

## レビュー対象の特定

$ARGUMENTS の内容に応じて、レビュー対象を決定する：

- **PR番号またはURLが指定された場合**: そのPRの差分をレビュー対象とする
- **指定がない場合**: 現在のブランチの差分をレビュー対象とする。ベースブランチは以下の優先順で決定する：
  1. 現在のブランチに紐づくPRがあれば、そのPRのベースブランチを使用
  2. PRがなければ、リポジトリのデフォルトブランチ（main または master）を使用

## コンテキスト収集（必ず実施）

レビューの精度を上げるために、差分だけでなくプロジェクト全体のコンテキストを収集してください。
以下の手順を **すべて** 実行してから、チェックリストに進んでください。

### Step 1: プロジェクト構成の把握
1. CLAUDE.md、README.md があれば読み、プロジェクトの規約・方針を理解する
2. docs/ 配下に設計ドキュメントがあれば目を通し、アーキテクチャと仕様を把握する
3. 変更に関連するフレームワーク・ライブラリの公式ドキュメント（特にセキュリティガイド）を必要に応じて参照する
   - React: https://react.dev/reference/react-dom/components/common#dangerously-setting-the-inner-html
   - Django: https://docs.djangoproject.com/en/5.2/topics/security/
   - OWASP Top 10: https://owasp.org/Top10/

### Step 2: 変更差分の取得

**PRを対象とする場合:**
1. `gh pr view` でPRのタイトル、説明、ベースブランチ、ヘッドブランチを取得する
2. `gh pr diff` で変更ファイル一覧と差分の詳細を取得する

**現在のブランチを対象とする場合:**
1. ベースブランチとの差分で変更ファイル一覧と差分の詳細を取得する

**共通:**
- 変更ファイルの **全体** を読み取る（差分行だけでなくファイル全文）

### Step 3: ドメイン自動判定
変更ファイルの拡張子・ディレクトリから、該当するドメインを判定する。
複数ドメインにまたがる場合はすべて適用する。

| ドメイン | 判定条件の例 |
|---------|------------|
| Web フロントエンド | `.tsx`, `.ts`, `.jsx`, `.js`, `.css`, `.html` かつ `src/`, `app/`, `components/`, `pages/` 等 |
| サーバーサイド | `.py`, `.go`, `.java`, `.rb`, `.rs` かつ `api/`, `server/`, `backend/`, `models/`, `services/` 等、または `views.py`, `urls.py`, `schema.py` 等 |
| インフラ | `.tf`, `.yml`, `.yaml`, `Dockerfile`, `docker-compose.*`, `.github/workflows/`, `helm/`, `k8s/` 等 |
| モバイル | `.swift`, `.kt`, `.dart`, `*.xcodeproj`, `android/`, `ios/`, React Native の `native` ディレクトリ等 |

判定したドメインをレビュー結果の冒頭に明記すること。

### Step 4: 影響範囲の調査
変更されたファイルごとに以下を調査する：
1. **呼び出し元・参照元**: 変更した関数、コンポーネント、型、定数を import/使用しているファイルを検索し、変更の影響が波及していないか確認する
2. **関連テスト**: 変更したコードに対応するテストファイルを特定し、テストが変更を反映しているか確認する
3. **同種の既存実装**: プロジェクト内の類似コード（同じディレクトリの他ファイル、同種のコンポーネントやAPI等）を確認し、パターンの一貫性を検証する

### Step 5: 設定・依存の確認
1. package.json、requirements.txt 等に変更がある場合、追加・更新されたライブラリを確認する
2. 設定ファイル（tsconfig.json、.eslintrc、docker-compose.yml 等）に変更がある場合、影響を確認する

## 共通チェックリスト（全ドメイン共通）

### 1. 設計・アーキテクチャ
- [ ] 変更の責務が明確で、単一責任の原則に沿っているか？
- [ ] 既存のアーキテクチャパターン（レイヤー構成、ディレクトリ構造）に準拠しているか？
- [ ] 仕様書やIssueに記載のない実装、根拠のない実装をしていないか？
- [ ] 過剰な抽象化や過剰設計（YAGNI違反）をしていないか？
- [ ] 後方互換性を破壊する変更がある場合、マイグレーション手順が用意されているか？

### 2. コード品質
- [ ] 変数名・関数名・クラス名がプロジェクトの命名規則に沿い、意図が明確か？
- [ ] 未使用の変数、関数、import がないか？
- [ ] 到達しないデッドコードがないか？
- [ ] コードの重複（コピペ実装）がないか？
- [ ] console.log やデバッグ用コード、TODO/FIXME コメントが残っていないか？
- [ ] ハードコードされた値（URL、ポート番号、マジックナンバー等）が定数や環境変数に切り出されているか？
- [ ] コメントは「なぜ」を説明しており、コードから読み取れる「何を」の説明になっていないか？
- [ ] 不要なファイル（空ファイル、不要な .gitkeep、一時ファイル等）がコミットされていないか？
- [ ] 多言語対応プロジェクトの場合、UIに表示される文字列がハードコードされず i18n 機構を通しているか？

### 3. セキュリティ
- [ ] シークレット情報（APIキー、トークン、パスワード）がコードやコミット履歴に含まれていないか？
- [ ] 認証・認可のチェックが適切に行われているか？
- [ ] 機密情報がログやエラーメッセージに出力されていないか？
- [ ] 外部入力（リクエストパラメータ、URL、ファイル）のバリデーション・サニタイズが行われているか？
- [ ] PII の取り扱いがプロジェクトのルール（common-design.md 5.1）に準拠しているか？（ログマスキング、URL に PII を含めない等）
- [ ] セキュリティヘッダー（CSP, HSTS, X-Frame-Options, X-Content-Type-Options）が適切に設定されているか？
- [ ] CORS 設定でワイルドカード（`*`）を使用していないか？
- [ ] 暗号化・ハッシュに安全なアルゴリズムを使用しているか？（`Math.random()` をセキュリティ用途に使っていないか）
- [ ] オープンリダイレクトの脆弱性がないか？（ユーザー入力由来の URL をリダイレクト先にしていないか）
- [ ] セキュリティに深く関わる変更がある場合、`/security-review` による詳細分析を検討したか？

### 4. エラーハンドリング
- [ ] 異常系（API失敗、タイムアウト、ネットワークエラー）の処理が実装されているか？
- [ ] 境界値・エッジケース（空配列、null、0、空文字、上限値）が考慮されているか？

### 5. テスト
- [ ] プロジェクトのテスト・リンター・フォーマッターを実行し、すべてパスしているか？（実行コマンドは package.json の scripts、Makefile、CI設定等から特定する）
- [ ] 変更に対応するテストが追加・更新されているか？
- [ ] カバレッジツールが利用可能な場合、テストカバレッジが低下していないか？
- [ ] テストが実装の詳細ではなく、振る舞い（入力と出力）を検証しているか？

### 6. 依存ライブラリ（新規追加・更新時のみ）
- [ ] プロジェクトの脆弱性チェックツールで既知の脆弱性がないか？（実行コマンドはCI設定等から特定する）
- [ ] 非推奨（deprecated）または開発停止のライブラリを追加していないか？
- [ ] ライブラリのバージョンは最新の安定版を利用しているか？
- [ ] ライセンスがプロジェクトの方針と互換性があるか？（GPL混入等）
- [ ] 既存の依存で代替可能な機能を、新たなライブラリで追加していないか？

### 7. ドキュメント
- [ ] README.md や docs 配下のドキュメントと実装の間に不整合がないか？
- [ ] 新機能の追加や設定変更があった場合、ドキュメントが更新されているか？
- [ ] API の変更がある場合、API仕様書（OpenAPI等）が更新されているか？

### 8. API 設計の一貫性
- [ ] API のレスポンス形式（ステータスコード、エラー構造）がプロジェクトの規約に統一されているか？
- [ ] ページネーション・ソートのパラメータ名が既存 API と一貫しているか？
- [ ] 命名規則（URL パス: kebab-case、レスポンスフィールド: snake_case）が守られているか？

### 9. 可観測性
- [ ] 構造化ログが適切に出力されているか？（リクエストID、ユーザーID 等のコンテキスト付き）
- [ ] 重要な業務操作（ユーザー作成、権限変更、削除等）の監査ログが出力されているか？

## ドメイン別チェックリスト（該当ドメインのみ適用）

### Web フロントエンド

#### 型安全性
- [ ] any, unknown, as による型アサーションを安易に使用していないか？
- [ ] 新規・変更コードに適切な型定義がされているか？（Props、状態、APIレスポンス）
- [ ] null / undefined の可能性があるケースが型レベルで考慮されているか？

#### セキュリティ
- [ ] ユーザー入力のサニタイズが行われているか？（XSS: dangerouslySetInnerHTML、v-html 等）
- [ ] CORS、CSRF 対策が適切か？
- [ ] sensitive data（トークン等）を localStorage / sessionStorage に保存していないか？（メモリまたは httpOnly Cookie を使用）
- [ ] `window.postMessage` 使用時に origin を検証しているか？
- [ ] 外部スクリプトの読み込みに SRI（Subresource Integrity）を使用しているか？
- [ ] ユーザー入力由来の URL を `href` や `window.open` に渡す際に検証しているか？（`javascript:` スキーム等）

#### パフォーマンス
- [ ] 不要な再レンダリングが発生していないか？（React: useMemo/useCallback の適切な使用、依存配列の正確性）
- [ ] APIリクエストの重複やウォーターフォールが発生していないか？
- [ ] 大量データの表示に仮想スクロールやページネーションが考慮されているか？

#### UX・エラー表示
- [ ] エラー時のユーザーへのフィードバック（エラーメッセージ、フォールバックUI）が適切か？
- [ ] ローディング状態が表示されているか？
- [ ] async/await の try-catch、Promise の reject が適切にハンドリングされているか？

- [ ] インタラクティブ要素に適切な aria 属性やセマンティックHTML が使用されているか？
- [ ] キーボード操作で全機能にアクセスできるか？

- [ ] 対象ブラウザで未サポートのAPI・CSS機能を使用していないか？

## 出力フォーマット

レビュー結果を以下のフォーマットで報告してください。

### 検出ドメイン
変更ファイルから判定したドメインを明記。（例: Web フロントエンド、サーバーサイド）

### サマリ
変更全体の概要と総合評価を1-2文で記述。

### 指摘事項

各指摘を以下の表形式で一覧化：

| # | 重要度 | カテゴリ | ファイル:行番号 | 指摘内容 |
|---|--------|---------|----------------|---------|

各指摘の詳細と修正案を表の後に記述：

> **#1 [指摘タイトル]**
> 修正案: ...

重要度は以下の3段階：
- **Critical**: マージ前に必ず修正が必要（セキュリティ、バグ、データ損失リスク）
- **Warning**: 修正を強く推奨（パフォーマンス、設計上の問題、保守性）
- **Info**: 改善提案（命名、コードスタイル、ドキュメント）

指摘がない場合は「指摘事項なし」と記載する。

### チェックリスト結果

適用した共通チェックリスト + ドメイン別チェックリストの各カテゴリについて、問題なし/指摘ありを一覧表示。

### 良い点

変更の中で特に良いと思った点があれば記述。
