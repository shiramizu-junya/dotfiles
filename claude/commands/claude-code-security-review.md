OWASP Top 10 (2021) に準拠したセキュリティレビューを実施してください。

## レビュー対象の特定

$ARGUMENTS の内容に応じて、レビュー対象を決定する：

- **PR番号またはURLが指定された場合**: そのPRの差分をレビュー対象とする
- **指定がない場合**: 現在のブランチの差分をレビュー対象とする。ベースブランチは以下の優先順で決定する：
  1. 現在のブランチに紐づくPRがあれば、そのPRのベースブランチを使用
  2. PRがなければ、リポジトリのデフォルトブランチ（main または master）を使用

## Step 1: セキュリティコンテキスト収集

以下を **すべて** 実行してから、チェックリストに進むこと。

### 1-1. プロジェクトのセキュリティポリシー
1. CLAUDE.md、README.md を読む
2. docs/common-design.md の Section 5「セキュリティ共通方針」を読む（PII 準拠マトリクス、禁止事項テーブルを把握）
3. docs/backend-design.md の認証・認可設計を読む

### 1-2. 変更差分の取得

**PRを対象とする場合:**
1. `gh pr view` でPRのタイトル、説明、ベースブランチ、ヘッドブランチを取得する
2. `gh pr diff` で変更ファイル一覧と差分の詳細を取得する

**現在のブランチを対象とする場合:**
1. ベースブランチとの差分で変更ファイル一覧と差分の詳細を取得する

**共通:**
- 変更ファイルの **全体** を読み取る（差分行だけでなくファイル全文）

### 1-3. データフロー分析
変更されたコードについて、データの流れを追跡する：
1. **入力**: データがどこから来るか（リクエストパラメータ、URL、ファイル、外部API）
2. **検証**: バリデーション・サニタイズが行われているか
3. **処理**: データがどのように変換・加工されるか
4. **保存**: データがどこに保存されるか（DB、ファイル、キャッシュ）
5. **出力**: データがどこに出力されるか（レスポンス、ログ、外部API）

### 1-4. 公式リファレンスの参照
変更内容に関連するフレームワーク・ライブラリのセキュリティガイドを参照する：
- OWASP Top 10: https://owasp.org/Top10/
- Django Security: https://docs.djangoproject.com/en/5.2/topics/security/
- React Security: https://react.dev/reference/react-dom/components/common#dangerously-setting-the-inner-html
- Node.js Security: https://nodejs.org/en/learn/getting-started/security-best-practices

## Step 2: OWASP Top 10 チェックリスト

各カテゴリについて、変更差分に該当する問題がないか精査する。
該当しないカテゴリは「該当なし」と判定してよい。

### A01: アクセス制御の不備 (Broken Access Control)
- [ ] 認証が必要なエンドポイントに認証チェックがあるか？
- [ ] 認可チェック（ロールベース、リソース所有者チェック）が適切か？
- [ ] IDOR（Insecure Direct Object Reference）: 他ユーザーのリソースにアクセスできないか？
- [ ] ディレクトリトラバーサル / パストラバーサルの脆弱性がないか？
- [ ] CORS 設定が適切か？（ワイルドカード `*` を使用していないか）
- [ ] HTTP メソッドの制限が適切か？（不要な PUT/DELETE が公開されていないか）

### A02: 暗号化の失敗 (Cryptographic Failures)
- [ ] 機密データ（パスワード、トークン、PII）が平文で保存・送信されていないか？
- [ ] 安全なハッシュアルゴリズムを使用しているか？（MD5/SHA1 をパスワードに使用していないか）
- [ ] `Math.random()` や `random` モジュールをセキュリティ用途に使用していないか？
- [ ] TLS/HTTPS が強制されているか？
- [ ] 暗号化キーがハードコードされていないか？

### A03: インジェクション (Injection)
- [ ] SQL インジェクション: ORM/パラメータバインドを使用し、生SQLにユーザー入力を直接埋め込んでいないか？
- [ ] XSS: ユーザー入力がサニタイズされずにHTML出力されていないか？（dangerouslySetInnerHTML、v-html 等）
- [ ] コマンドインジェクション: `os.system()`, `subprocess` 等にユーザー入力を渡していないか？
- [ ] LDAP / NoSQL / XPath インジェクションの可能性がないか？
- [ ] テンプレートインジェクション（SSTI）の可能性がないか？
- [ ] ヘッダーインジェクション（CRLF）の可能性がないか？

### A04: 安全でない設計 (Insecure Design)
- [ ] ビジネスロジックの不備（権限昇格、ステップスキップ、値の改ざん）がないか？
- [ ] Rate Limiting が必要な操作（ログイン、パスワードリセット、API呼び出し）に設定されているか？
- [ ] 入力バリデーションがホワイトリスト方式で実装されているか？
- [ ] フェイルセーフ設計: エラー時にデフォルトでアクセスを拒否するか？

### A05: セキュリティの設定ミス (Security Misconfiguration)
- [ ] デバッグモード / 詳細エラーメッセージが本番環境で無効化されているか？
- [ ] セキュリティヘッダー（CSP, HSTS, X-Frame-Options, X-Content-Type-Options）が設定されているか？
- [ ] 不要な機能・エンドポイント・ポートが無効化されているか？
- [ ] デフォルトのクレデンシャルやアカウントが残っていないか？
- [ ] エラーレスポンスにスタックトレースや内部実装の詳細が含まれていないか？

### A06: 脆弱で古いコンポーネント (Vulnerable and Outdated Components)
- [ ] 既知の脆弱性を持つライブラリを使用していないか？
- [ ] 依存パッケージのバージョンが最新の安定版か？
- [ ] 非推奨（deprecated）または開発停止のライブラリを追加していないか？

### A07: 識別と認証の失敗 (Identification and Authentication Failures)
- [ ] JWT の検証（署名、有効期限、issuer）が適切か？
- [ ] セッション管理が安全か？（セッションIDの再生成、タイムアウト）
- [ ] パスワードポリシー（最小長、複雑性）が適用されているか？
- [ ] ブルートフォース対策（アカウントロック、遅延）が実装されているか？
- [ ] sensitive data（トークン等）が localStorage / sessionStorage に保存されていないか？

### A08: ソフトウェアとデータの整合性の失敗 (Software and Data Integrity Failures)
- [ ] デシリアライゼーション（pickle, YAML.load, eval 等）にユーザー入力を渡していないか？
- [ ] CI/CD パイプラインの整合性が保たれているか？
- [ ] 外部スクリプト・CDN の読み込みに SRI（Subresource Integrity）を使用しているか？
- [ ] Mass Assignment を防止しているか？（ホワイトリスト制御）

### A09: セキュリティログと監視の失敗 (Security Logging and Monitoring Failures)
- [ ] 認証の成功・失敗がログに記録されているか？
- [ ] 権限変更・データ削除等の重要操作が監査ログに記録されているか？
- [ ] ログに PII や機密情報が含まれていないか？（マスキング）
- [ ] ログの改ざん防止策が講じられているか？

### A10: サーバーサイドリクエストフォージェリ (SSRF)
- [ ] ユーザー入力由来の URL を使ってサーバーからリクエストを発行していないか？
- [ ] 外部 URL の呼び出し時にドメインのホワイトリスト検証を行っているか？
- [ ] 内部ネットワーク（127.0.0.1, 10.x.x.x, 169.254.169.254 等）へのアクセスをブロックしているか？

## Step 3: プロジェクト固有のセキュリティチェック

### PII 準拠チェック
common-design.md Section 5.1 の PII 準拠マトリクスと照合し、以下を確認：
- [ ] PII データのログ出力時にマスキングが適用されているか？
- [ ] URL パスやクエリパラメータに PII が含まれていないか？
- [ ] PII の保存・送信時に暗号化が適用されているか？
- [ ] PII の保持期間・削除ポリシーが遵守されているか？

### 禁止事項チェック
common-design.md Section 5.2 の禁止事項テーブルと照合し、違反がないことを確認する。

### JWT ライフサイクル
- [ ] アクセストークンの有効期限が適切に短いか？
- [ ] リフレッシュトークンの管理が安全か？（httpOnly Cookie、ローテーション）
- [ ] トークンの失効（ログアウト、パスワード変更時）が正しく処理されているか？
- [ ] JWT ペイロードに不要な機密情報が含まれていないか？

## Step 4: 自動ツール実行

変更内容に応じて、以下のツールを実行し結果を報告する：

### 依存パッケージの脆弱性チェック
- **npm プロジェクト**: `npm audit` を実行
- **Python プロジェクト**: `pip audit` を実行（インストールされている場合）

### シークレット検索
変更ファイルに対して、以下のパターンを検索する：
- API キー・トークンのパターン（`[A-Za-z0-9_-]{20,}` 等）
- `password`, `secret`, `api_key`, `token` 等のハードコード
- `.env` ファイルのコミット
- プライベートキーファイル（`.pem`, `.key`）のコミット

#### 検出された脆弱性・リスク

各指摘を以下の表形式で一覧化：

| # | Severity | OWASP カテゴリ | ファイル:行番号 | 脆弱性の概要 |
|---|----------|---------------|----------------|-------------|

Severity は以下の4段階：
- **Critical**: 即座に悪用可能な脆弱性（認証バイパス、SQLインジェクション、RCE 等）
- **High**: 悪用条件は限定的だが重大な影響がある脆弱性（XSS、IDOR、情報漏洩 等）
- **Medium**: 直接的な悪用は困難だが修正すべきセキュリティ上の問題（設定ミス、弱い暗号化 等）
- **Low**: ベストプラクティスからの逸脱、防御的な改善提案

各指摘の詳細を表の後に記述：

> **#1 [脆弱性タイトル]**
> - **Severity**: Critical / High / Medium / Low
> - **OWASP**: A01 / A02 / ... / A10
> - **影響**: この脆弱性が悪用された場合の影響
> - **再現手順**: 攻撃者が脆弱性を悪用する手順の概要
> - **修正案**: 具体的なコード修正案

検出された脆弱性がない場合は「検出された脆弱性なし」と記載する。

#### プロジェクト固有チェック結果

#### 自動ツール実行結果
npm audit / pip audit / シークレット検索の結果を報告。

#### 推奨事項
